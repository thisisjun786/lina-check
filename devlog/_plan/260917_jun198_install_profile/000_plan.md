## 범위

1. 대상 저장소 프로필 스키마와 설정 진입점. 기본값은 비어 있고 빈 목록은 거부한다.
   원본의 OpenClaw 운영 계정·서비스·대상을 새 진입점으로 복사하지 않는다.
2. 브랜딩 진입점. 원본 문자열을 설치별로 바꿀 수 있는 자리를 만든다.
3. 개인 소유자 이름 기반 허용 판정을 전수 조사하고 설정 기반으로 옮긴다.
4. 상태·큐·대시보드 연결은 원본 방식을 따른다. Worker 와 R2 구조를 보존하고 미설정으로 둔다.
5. GitHub App 이 실제로 필요한 권한 범위를 소스의 실제 호출에서 도출해 문서화한다.
6. Worker 설정이 아직 원본 저장소를 가리키는 문제를 해소한다.

범위 밖. App 생성·설치, Worker/R2 프로비저닝, 실제 대상 저장소 값 선정, 운영 활성화,
워크플로 되살리기, 모델 호출, 배포. 전부 활성화 단계다.

## 이 과제가 실제로 부딪히는 문제

JUN-135 가 남긴 검증기는 upstream 파일의 바이트가 하나도 바뀌지 않았음을 단정한다.
`scripts/check-scaffold.mjs` 의 바이트 루프가 upstream 항목 1646건 중 `package.json` 과
`.gitignore` 만 빼고 1644건을 대조한다.

그런데 이 과제가 옮겨야 하는 판정은 전부 upstream 파일 안에 있다.
`src/hosted-target-admission.ts` 의 소유자 집합 리터럴, `dashboard/worker.ts` 의 웹훅 허용 판정,
`dashboard/wrangler.toml` 의 계정·도메인·대상 값이다. 설정으로 옮기려면 그 파일들을 고쳐야 하고,
고치는 순간 현재 검증기는 거부한다.

따라서 이 과제의 첫 단위는 기능이 아니라 검증기다. JUN-135 가 신규 파일에 대해 만든
"코드가 집합을 고정하고 config 가 근거를 갖는다" 구조를 upstream 수정에도 똑같이 적용한다.
새 기제를 만들지 않고 같은 기제를 한 층 넓힌다.

## 계약

### C1 · 수정한 upstream 파일은 선언된 것만 허용한다

`scripts/lina-check-derived-contract.mjs` 의 `MODIFIED_UPSTREAM_FILES` 리터럴이 집합을 고정한다.
`config/lina-check-scaffold.json` 의 `derived.modifiedUpstreamFiles` 는 항목마다 근거만 갖는다.
선언과 리터럴이 다르면 거부한다.

### C2 · 선언하지 않은 upstream 파일은 바이트가 같아야 한다

기존 단정을 그대로 둔다. 선언된 파일만 바이트 대조에서 빠진다.

### C3 · 선언했는데 안 바뀐 파일은 거부한다

선언은 실제 수정을 동반해야 한다. 바이트가 upstream 과 같은데 선언에만 남아 있으면
`modified-upstream-unchanged` 로 거부한다. 낡은 선언이 예외 범위를 조용히 넓히는 것을 막는다.

### C4 · 모드는 계속 대조한다

수정을 허용하는 것은 내용이지 실행 권한이나 심링크 여부가 아니다.

### C5 · 우리가 소유한 코드·설정에는 개인 계정 이름이 없다

파생 파일과 수정한 upstream 파일 중 `src/`, `dashboard/`, `config/`, `schema/`, `scripts/` 아래
항목에 금지 리터럴이 없어야 한다. 금지 대상은 개인 소유자 계정 이름, 원본 Cloudflare 계정 ID,
원본 App client ID, 원본 운영 도메인, 원본 레지스트리 URL 이다.

`devlog/` 와 `docs/` 의 산문은 이 검사에서 뺀다. 무엇을 제거했는지 적는 문서가 그 이름을
쓰지 못하면 기록이 성립하지 않는다. 손대지 않은 upstream 파일도 뺀다. 그쪽은 C2 가 바이트로
이미 고정하고 있고, 원본 보존이 이 저장소의 계약이다.

### C6 · 출고되는 설치 설정은 비어 있다

`config/lina-check-installation.json` 은 `configured: false` 이고 모든 목록이 비어 있어야 한다.
`check:scaffold` 가 정적으로 확인한다. 값이 들어간 채로 머지되는 것을 막는다.

### C7 · 비어 있는 설치 설정은 거부한다

로더는 미설정 프로필로 허용 판정을 내주지 않는다. 빈 목록은 통과가 아니라 거부다.
거부 경로마다 `lina:contract-selftest` 이 픽스처로 실제 거부를 관측한다.

### C8 · 기존 단정을 삭제하지 않는다

JUN-135 의 단정 26건은 그대로 둔다. 넓히는 단정이 있으면 넓힌 만큼 새 단정으로 다시 좁힌다.
`lina:contract-selftest` 의 `assertionCalls` 경고가 계속 동작해야 한다.

감사가 준 선택지 중 "명시적으로 유예하고 주장을 좁힌다" 대신 "공유 전송 경계를 만든다" 를 택했다.
호출부 6곳에 문을 다는 것보다 좁고, 새 호출부가 생겨도 같은 문을 지나기 때문이다.
유예는 GitHub 경로가 아닌 JWKS 한 건으로 한정했다.

## A 감사 3회전 기록과 주장 범위 확정

3회전도 `FAIL` 이고 차단 2건인데, 둘 다 "덮어라, 아니면 주장을 좁히고 유예를 기록하라" 는
같은 선택지를 준다. 감사가 직접 적었다. 차단된 패키지 명령은 유예를 정당화하지만
설치 기반 인가를 성립시키지는 않는다. 맞는 말이고, 그래서 주장을 좁힌다.

덮는 쪽을 택하지 않은 이유는 범위다. 원본 트리 전체의 전송과 독립 진입점을 전부 설치 게이트
뒤로 옮기는 것은 활성화 단계의 일이고, 이 이슈가 명시적으로 제외한 범위다. 유예를 감추지
않고 위치와 근거를 목록으로 남기는 쪽이 정직하다.

### 이 과제가 주장하는 것

| # | 주장 | 범위 |
| -- | -- | -- |
| a | 설치 설정이 허용 판정의 권위다 | 호스티드 대상 적격 판정과 웹훅 저장소 적격 판정. `030` 의 수정 집합 7개가 덮는 경로 |

| c | 설정이 원본 저장소를 가리키지 않는다 | 새 설치 프로필과 `dashboard/wrangler.toml` |

### 이 과제가 주장하지 않는 것

- 미설정 Worker 의 실제 바깥 요청이 0건이다. Worker 런타임이 이 단계의 게이트에 없다.
- Node 쪽 전송 7개가 설치 게이트 뒤에 있다. `040` 에 목록과 유예 근거가 있다.
- 독립 진입점 2개가 설치 게이트 뒤에 있다. `010` 에 목록과 유예 근거가 있다.
- `config/target-repositories.json` 이 원본 대상을 더는 담지 않는다. 그 파일은 upstream
  보존 대상이고 원본 대상을 그대로 담는다. 바뀌는 것은 그 내용이 더는 권한이 아니라는 점이다.

유예한 것을 "덮었다" 고 적지 않는다. 차단 명령 뒤에 있다는 사실은 사고를 막는 장치이지
인가 모형이 아니다. 그 구분을 `POLICY.md` 가 이미 하고 있고 여기서도 그대로 지킨다.

원본 전체 `test`/`check` 는 계속 parked 다. 돌리지 않고, 통과했다고 보고하지 않는다.
